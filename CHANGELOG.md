# Changelog

All notable changes to KopiQueue are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Fixed

- Concurrent bulk inserts of the same unique jobs in different orders no longer deadlock on PostgreSQL. Rows are inserted in unique-key order, while inserted jobs keep ids in input order. ([#46](https://github.com/sujanto-gaws/KopiQueue/issues/46))

### Changed

- Clean-room (ADR-008): River is a reference only, and KopiQueue's tests and CI no longer run a River client or River's CLI. The River interop suite (`RiverInteropTests`, `tests/compat/go`), the tests that ran River's CLI against the main line, and the spike 0.8 Go harness are removed, and CI no longer installs Go. The migration tests still compare every version, up and down, with the catalog goldens recorded from River v0.51.2. The state-bitmask check now compares against a recorded truth table.

### Added

- Args-level default insert options (FR-DEF-05):
  - An args type implementing `IJobArgsWithInsertOptions` supplies its own queue, priority, attempts, tags, metadata and uniqueness.
  - Each option an insert sets still wins.
  - ([#45](https://github.com/sujanto-gaws/KopiQueue/issues/45))
- Admin API (FR-ADM-01 to FR-ADM-05, FR-ERR-07):
  - **`JobGetAsync`.**
  - **`JobListAsync`:** filters by IDs, kinds, queues, states, priorities and metadata; sorts by ID or one of the job's times, either way; keyset pages through `NextCursor`.
  - **`JobDeleteAsync`:** refuses a running job.
  - **`JobDeleteManyAsync`.**
  - **`JobRetryAsync`:** makes a scheduled, retryable or finalised job available now.
  - **Transaction variants:** every admin call that changes data has an overload taking the caller's transaction, the queue calls included.
  - ([#44](https://github.com/sujanto-gaws/KopiQueue/issues/44))
- Periodic jobs (FR-PER-01 to FR-PER-04):
  - **Schedules:** `PeriodicSchedule.Every(interval)`, or `PeriodicSchedule.Cron(expression, timeZone)` on Cronos (5 or 6 fields, macros, River's `CRON_TZ=` prefix).
  - **Jobs:** `PeriodicJob`, with `RunOnStart` and `Id`.
  - **Registration:** `KopiClientOptions.PeriodicJobs` and `KopiQueueBuilder.AddPeriodicJob`. At runtime, `KopiClient.PeriodicJobs` adds and removes jobs.
  - **Leader only:** only the leader inserts them, each tick once, also across a change of leader. A new leader catches up a recent tick the previous one may have missed.
  - **Metadata:** inserted jobs carry `"periodic": true`.
  - ([#43](https://github.com/sujanto-gaws/KopiQueue/issues/43))
- Unique jobs (FR-UNQ-01 to FR-UNQ-06):
  - **Options:** `InsertOptions.Unique` takes a `UniqueOptions` (`ByArgs`, `ByPeriod`, `ByQueue`, `ByState`, `ExcludeKind`). Options with nothing set enforce nothing, as in River.
  - **Marked members:** `[UniqueKey]` limits `ByArgs` to the marked members, under the JSON names the serialiser writes (`IJobArgsSerializer.GetUniqueMemberNames`).
  - **Encoding:** `KopiClientOptions.UniqueArgsEncoding` chooses how arg values are written into the key.
  - **Duplicates:** a duplicate insert returns the job that holds the key, with `UniqueSkippedAsDuplicate` set, and inserts nothing, singly and in `InsertManyAsync`, including duplicates within one batch.
  - **Enforcement:** PostgreSQL enforces the key with River's partial unique index, so KopiQueue and River producers that share a database dedupe against each other.
  - **Fast insert:** `InsertManyFastAsync` rejects unique jobs.
  - ([#42](https://github.com/sujanto-gaws/KopiQueue/issues/42))
- Unique key builder and unique-states bitmask (FR-UNQ-01, FR-UNQ-04, FR-UNQ-06), the groundwork for unique jobs (M4). It reproduces all 22 unique keys River v0.51.2 computed in spike 0.8. DQ-8 is decided: arg values are re-encoded as Go's `encoding/json` writes them, so the key doesn't depend on how the args were serialised, and .NET and Go producers of the same args share a key. Nothing public changes yet; unique inserts arrive with task 4.2. ([#41](https://github.com/sujanto-gaws/KopiQueue/issues/41), [#79](https://github.com/sujanto-gaws/KopiQueue/issues/79))
- External job cancel (FR-ERR-06, FR-ADM-05, FR-DB-05): `IKopiClient.JobCancelAsync(id)`, and an overload that takes the caller's `DbTransaction`, so the cancel commits or rolls back with it. They return the job's row after the call and throw `KopiQueueNotFoundException` for an unknown id.
  - A job that has not started is cancelled at once and never runs.
  - A running job gets `metadata.cancel_attempted_at`, and the client running it cancels the worker's `CancellationToken`: through a `river_control` notification, or within `FetchPollInterval` without notifications. A worker that then throws, its token's `OperationCanceledException` included, cancels the job for good with that exception as its error. A worker that returns completes it. A retry, snooze or interruption recorded after the cancel becomes `cancelled`.
  - A finalised job is returned as it is.
  - The driver API gains `IKopiExecutor.JobCancelAsync` and `JobListCancelAttemptedAsync` (experimental, `KQ0001`). ([#39](https://github.com/sujanto-gaws/KopiQueue/issues/39))
- Job cleaner (FR-MNT-04): the leader deletes completed, cancelled and discarded jobs once their `finalized_at` is older, by the database's clock, than their state's retention. It runs every 30 seconds, in batches of up to 1,000, oldest first. New options `KopiClientOptions`/`KopiQueueOptions.CompletedJobRetention` (default 24 hours), `CancelledJobRetention` (24 hours) and `DiscardedJobRetention` (7 days). Each is positive, or `null` to keep that state's jobs forever. Jobs in other states are never deleted. Rows another transaction holds are skipped and deleted by a later batch. Deleting a completed unique job frees its unique slot. **Upgrade note:** finalised jobs used to stay forever; with the defaults, the leader now deletes them. Set the retentions to `null` to keep the old behaviour. The driver API gains `IKopiExecutor.JobDeleteFinalizedAsync` and `JobDeleteFinalizedParams` (experimental, `KQ0001`). ([#37](https://github.com/sujanto-gaws/KopiQueue/issues/37))
- Rescuer (FR-MNT-03, NFR-REL-02): the leader rescues jobs left `running` by a client that crashed or lost its connection, every minute in batches of up to 1,000. A job is stuck once its attempt is older, by the database's clock, than `KopiClientOptions.RescueStuckJobsAfter` (default `JobTimeout` + 1 hour, and at least the worker's own timeout). A job with no timeout is never rescued by age. A stuck job with attempts left is retried by the same rules as a failed attempt; one without is discarded. Either way the stuck attempt counts and an error says why. A job whose kind this client has no worker for is rescued with the client's defaults, not discarded. Only a job still running the attempt the rescuer read is changed. Delivery is at least once: the stuck attempt may still be running somewhere, so `RescueStuckJobsAfter` also bounds how long a job may run. The driver API gains `IKopiExecutor.JobListStuckAsync`, `JobRescueManyAsync`, `JobListStuckParams`, `JobListStuckResult` and `JobRescueParams` (experimental, `KQ0001`); `KopiQueueOptions` gains `RescueStuckJobsAfter`. ([#36](https://github.com/sujanto-gaws/KopiQueue/issues/36))
- Scheduler (FR-SCH-01, FR-SCH-02, FR-MNT-02): the leader makes due `scheduled` and `retryable` jobs `available`, by the database's clock, every `KopiClientOptions.SchedulerInterval` (default 5 s, ±10% jitter) in batches of up to 10,000, skipping rows another transaction holds. Each queue that got jobs is notified once, on commit. A retryable unique job whose slot a duplicate took while it waited is discarded, with an error saying why. The executor uses the same interval for retries and snoozes it makes available at once. The driver API gains `IKopiExecutor.JobScheduleAsync`, `JobScheduleParams` and `JobScheduleResult` (experimental, `KQ0001`); `KopiQueueOptions` gains `SchedulerInterval`. ([#35](https://github.com/sujanto-gaws/KopiQueue/issues/35))
- Queues, pause and resume (FR-QUE-02..04, FR-ADM-04, FR-DB-05): clients create the rows of the queues they work and mark them worked every minute. `IKopiClient` gains `QueueGetAsync`, `QueueListAsync`, `QueuePauseAsync`, `QueueResumeAsync` (`"*"` for all queues; `QueuePauseOptions.LocalOnly` for this client only) and `QueueUpdateAsync`, with `QueueRow`, `QueueListParams` and `KopiQueueNotFoundException`. A paused queue fetches nothing while its running jobs finish; the pause reaches other clients at once by notification, or within `FetchPollInterval` without one, and works both ways with River clients on the same schema. The driver API gains the queue operations (experimental, `KQ0001`). `QueueRetention` must now be at least 5 minutes. ([#38](https://github.com/sujanto-gaws/KopiQueue/issues/38))
- Queue cleaner (FR-MNT-05): the leader deletes the queue rows of queues no client has worked for `KopiClientOptions.QueueRetention` (default 24 hours; `null` keeps them), every minute in batches of up to 1,000. Their jobs are not touched. The driver API gains `IKopiExecutor.QueueDeleteExpiredAsync` and `QueueDeleteExpiredParams` (experimental, `KQ0001`); `KopiQueueOptions` gains `QueueRetention`. ([#37](https://github.com/sujanto-gaws/KopiQueue/issues/37))
- Maintenance (FR-MNT-07): the leader runs maintenance services in bounded batches of one statement each, repeating at once while batches are full and otherwise waiting the service's interval with ±10% jitter. They stop, and are waited for, before a leader that loses its lease steps down. The scheduler, rescuer and cleaners that run on it follow. ([#34](https://github.com/sujanto-gaws/KopiQueue/issues/34))
- Leader election (FR-MNT-01): a client that works jobs now competes for the leader lease in `river_leader`, which maintenance will run under from 0.3.0. It tries every `KopiClientOptions.ElectInterval` (default 5 s) and renews a lease of `LeaderTtl` (default 15 s, at least twice the interval). A leader that cannot renew steps down while a third of its lease is left, before another client can take over. On `StopAsync` it resigns and announces it on `<schema>.river_leadership` as River does, so another client, KopiQueue or River, takes over at once. A crashed leader is replaced once its lease expires. The driver API gains `IKopiExecutor.LeaderAttemptElectAsync`, `LeaderAttemptReelectAsync`, `LeaderResignAsync` and `LeaderElectParams` (experimental, `KQ0001`). `ClientId` is now limited to 127 characters. `KopiQueueOptions` gains `ElectInterval` and `LeaderTtl`. ([#33](https://github.com/sujanto-gaws/KopiQueue/issues/33))
- Hosting (FR-HST-01, -02, -04): `services.AddKopiQueue(kq => ...)` in `KopiQueue.Hosting` registers the client (as `KopiClient` and `IKopiClient`) and a hosted service that starts it with the host and stops it gracefully on shutdown. `KopiQueueBuilder` sets the driver, queues, workers (`AddWorker<TArgs, TWorker>()`), args serialiser (`UseJsonContext`) and retry policy; `BindConfiguration("KopiQueue")` binds `KopiQueueOptions` (queues, timeouts, modes) from configuration with source-generated binding, so it works in trimmed and Native AOT apps. An invalid configuration, or a missing driver, fails host startup with every problem listed. `KopiQueue.Npgsql` adds `UseNpgsql()` (the `NpgsqlDataSource` from DI), `UseNpgsql(dataSource)` and `UseKeyedNpgsql(key)`. New sample: `samples/WorkerService`. ([#29](https://github.com/sujanto-gaws/KopiQueue/issues/29))
- Working jobs (FR-HST-03, FR-DEF-06): `KopiClient.StartAsync` and `StopAsync` run the configured queues. `KopiClientOptions` gains `Queues` (with `QueueOptions.MaxWorkers`), `Workers`, `Services`, `LoggerFactory`, `ClientId`, `JobTimeout`, `RetryPolicy`, `FetchPollInterval`, `FetchCooldown`, `FetchBatchMax`, `NotificationMode` (`Auto`, `ListenNotify`, `PollOnly`), `CompleterMode` (`Batch`, `Async`, `Inline`), `SoftStopTimeout` and `HardStopGrace`. An invalid configuration fails `StartAsync` with `KopiQueueConfigurationException` before anything starts. `StopAsync` stops fetching, waits for running jobs until its token fires or `SoftStopTimeout` passes, then cancels them (they run again later without using an attempt), writes the pending outcomes and closes the notifier. A client without queues or workers stays insert-only. Scheduled jobs and later retries wait for the scheduler in 0.3.0. ([#28](https://github.com/sujanto-gaws/KopiQueue/issues/28))
- Completion (FR-EXE-06, NFR-REL-03): the driver API gains `IKopiExecutor.JobSetStateIfRunningManyAsync` and `JobSetStateParams` (experimental, `KQ0001`), River's statement for recording finished attempts: only jobs still running change, and a job whose cancellation was asked for while it ran ends cancelled. The client's internal completer writes outcomes in batches of up to 2,000 every 50 ms by default (or one by one, or inline), retries with backoff while the database is down, slows the producers down when it falls behind, and reports a completion only once it is stored. ([#27](https://github.com/sujanto-gaws/KopiQueue/issues/27))
- Job control and retries (FR-ERR-01..04): `throw JobControl.Cancel(reason)` from a worker cancels its job for good, and `throw JobControl.Snooze(delay)` runs it again later without using an attempt, counting snoozes in the job's `snoozes` metadata as River does. `JobCancelException` and `JobSnoozeException` are recognised even when wrapped. `IRetryPolicy` decides when a failed job runs again; `DefaultRetryPolicy` waits `n^4` seconds ±10% after the `n`th error, at most `MaxDelay` (default 24 hours). ([#26](https://github.com/sujanto-gaws/KopiQueue/issues/26))
- Job execution (FR-DEF-03, FR-EXE-05, FR-EXE-07, FR-EXE-08): the client's internal executor runs each fetched job in a new DI scope, with its args deserialised and its worker resolved there, under the worker's `Timeout` or the client's default of 1 minute. An exception or a timeout fails the attempt: the error is recorded with its message and stack trace, and the job is retried after the worker's `NextRetry` or the default backoff (`n^4` seconds for the `n`th error, ±10%, at most 24 hours) until its attempts run out, when it is discarded; a retry due within 5 s makes the job available at once. A hard stop interrupts the job instead: it runs again without using an attempt. These are River's rules, so jobs move the same way whichever library works them. Nothing a worker throws reaches the host. A job of a kind this client has no worker for is retried the same way, so during a rolling deploy another client can take it (DQ-3). ([#25](https://github.com/sujanto-gaws/KopiQueue/issues/25), [#75](https://github.com/sujanto-gaws/KopiQueue/issues/75))
- Fetching (FR-EXE-01..04): the driver API gains `IKopiExecutor.JobGetAvailableAsync` and `JobGetAvailableParams` (experimental, `KQ0001`). On PostgreSQL it locks due, available jobs of one queue with `FOR UPDATE SKIP LOCKED`, in `priority, scheduled_at, id` order, and starts them for the fetching client, so concurrent clients never get the same job. The client's internal per-queue producer fetches on insert notifications, on its own client's inserts and on a 1 s poll, never runs more than the queue's `MaxWorkers` jobs at once, fetches again at once after a full batch, and on stop waits for running jobs before cancelling them. Producers run jobs once the executor lands. ([#24](https://github.com/sujanto-gaws/KopiQueue/issues/24))
- Notifications (FR-EXE-03, FR-DB-04, NFR-REL-04a): the driver API gains `IKopiDriver.CreateListener()`, `IKopiListener`, `IKopiListenerConnection`, `NotificationTopic` and `KopiNotification` (experimental, `KQ0001`). The PostgreSQL driver listens on the River channels `<schema>.river_insert`, `river_control` and `river_leadership` over its own non-pooled connection, cloned from the data source with its credentials, with a TCP keep-alive that finds a silently dead connection in about twice `NpgsqlDriverOptions.NotifierKeepAlive` (default 5 s). `NpgsqlDriverOptions.NotifierConnectionString` routes that connection around PgBouncer or a proxy. A schema name too long for its channels (over 46 bytes) disables notifications instead of losing them silently. The client's internal notifier reconnects with backoff and wakes every subscriber after each reconnect; pooled inserts also wake the client's own producers directly. Producers start using both with the next task. ([#23](https://github.com/sujanto-gaws/KopiQueue/issues/23))
- Workers (FR-DEF-02, FR-DEF-04, FR-DEF-06): `IWorker<TArgs>` and the `Worker<TArgs>` base class with `WorkAsync(Job<TArgs>, CancellationToken)` and overridable `Timeout` and `NextRetry`; `Job<TArgs>`, the fetched row with its deserialised args; and `WorkerRegistry`, one worker per kind, added as a type created in each job's DI scope (`Add<TArgs, TWorker>()`, or `Add<TWorker>()` outside trimmed and AOT apps) or as a shared instance. Duplicate kinds, missing or invalid kinds and abstract worker types fail at registration with `KopiQueueConfigurationException`. Nothing runs workers yet; the executor follows in 0.2.0-alpha. ([#22](https://github.com/sujanto-gaws/KopiQueue/issues/22))

### Changed

- Requirements 0.5: a worker no longer sets a `MaxAttempts` default (FR-DEF-04); per-type defaults come from the args type (FR-DEF-05). DQ-1 is closed: `WorkAsync` returns `Task`. ([#22](https://github.com/sujanto-gaws/KopiQueue/issues/22), [#73](https://github.com/sujanto-gaws/KopiQueue/issues/73))

## [0.1.0-alpha.1] - 2026-11-26

First preview (milestone M1, schema and insert): migrate a PostgreSQL database to the River-compatible schema and insert jobs, alone, in bulk, or in the caller's Npgsql or EF Core transaction. Workers and job execution come in 0.2.0-alpha.

### Added

- Driver conformance suite (FR-DB-06, ADR-012): `DriverConformanceTests<TFixture>` holds the insert and migration cases every driver must pass, and the PostgreSQL driver passes them. A new driver adds a fixture and a one-line subclass. ([#21](https://github.com/sujanto-gaws/KopiQueue/issues/21))
- Args serialisation (NFR-COMP-06): `IJobArgsSerializer` and `SystemTextJsonArgsSerializer`, made from a `JsonSerializerContext` for trimmed and Native AOT apps, from `JsonSerializerOptions`, or the reflection-based `Default`; set through the new `KopiClientOptions.ArgsSerializer`. `KopiClientOptions` also takes the `TimeProvider`, which replaces `KopiClient`'s `timeProvider` constructor parameter. ([#20](https://github.com/sujanto-gaws/KopiQueue/issues/20))
- `KopiQueue.EntityFrameworkCore`: `InsertAsync`, `InsertManyAsync` and `InsertManyFastAsync` extension methods that insert jobs in a `DbContext`'s current transaction, so they commit or roll back with its changes. Provider-neutral (EF Core Relational only); a context without a transaction is rejected. ([#19](https://github.com/sujanto-gaws/KopiQueue/issues/19))
- Insert-only use (FR-INS-08): `KopiClient` inserts with no queues, workers or start step, and holds no connection or background work between inserts, so a web front-end can share one client or create one per request. ([#18](https://github.com/sujanto-gaws/KopiQueue/issues/18))
- Bulk insert: `InsertManyAsync` returns the stored jobs in order, and `InsertManyFastAsync` uses PostgreSQL binary `COPY` and returns the count. Both take `InsertRequest(args, options)` items of any job types, validate every job before inserting any, are all-or-nothing, and notify each queue once on commit. ([#17](https://github.com/sujanto-gaws/KopiQueue/issues/17))
- `KopiClient` and `IKopiClient` with `InsertAsync`, on a pooled connection or inside the caller's transaction, returning `InsertResult<TArgs>`. On PostgreSQL the insert notifies `<schema>.river_insert` for each queue with available jobs, in the same transaction, so listeners hear of it only on commit. ([#16](https://github.com/sujanto-gaws/KopiQueue/issues/16))
- Job model: the `IJobArgs` marker and `[JobKind]` attribute; `JobKindRegistry` (kind lookup, duplicate-kind detection); `InsertOptions` (`Queue`, `Priority`, `ScheduledAt`, `MaxAttempts`, `Tags`, `Metadata`) with `InsertDefaults`, validated before insert; `KopiQueueConfigurationException`. ([#15](https://github.com/sujanto-gaws/KopiQueue/issues/15))
- Driver API (experimental, `KQ0001`): `IKopiDriver`, `IKopiExecutor` with `JobInsertManyAsync` and `JobGetByIdAsync`, and `DriverCapabilities`, plus the job model `JobRow`, `JobState` and `AttemptError`. PostgreSQL driver `NpgsqlDriver` with `NpgsqlDriverOptions` (`Schema`, `TablePrefix`), on pooled connections or a caller's transaction. ([#14](https://github.com/sujanto-gaws/KopiQueue/issues/14))
- Migrator API: `KopiMigrator` with `MigrateAsync` (up or down, target version, dry run, lock timeout), `GetVersionsAsync` and `ValidateAsync`. For PostgreSQL, create one with `new NpgsqlDriver(dataSource, options).CreateMigrator()`. ([#13](https://github.com/sujanto-gaws/KopiQueue/issues/13))
- PostgreSQL: the River-compatible migration line `main`, versions 1–8, matching River v0.51.2. Every version leaves the same catalog as River's CLI, up and down, so KopiQueue and River can each continue a schema the other migrated. Works with a custom schema and table prefix. ([#12](https://github.com/sujanto-gaws/KopiQueue/issues/12))
- Migration engine: embedded, versioned up/down SQL per migration line, a lock so concurrent runners apply each version once, and one transaction per migration together with its version row. Failures raise `KopiQueueMigrationException`. ([#11](https://github.com/sujanto-gaws/KopiQueue/issues/11))
