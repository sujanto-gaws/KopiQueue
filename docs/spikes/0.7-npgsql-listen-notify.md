# Spike 0.7 — Npgsql LISTEN/NOTIFY for the notifier

**Date:** 2026-11-26 · **Plan task:** M0 / 0.7 · **Requirements:** FR-EXE-03, FR-INS-07, NFR-COMP-04, NFR-REL-* · **ADR:** 007
**Code:** `spikes/NpgsqlSpikes` (`latency`, `tx`, `payload`, `names`, `pool`, `terminate`, `blackhole`) · **Raw output:** [postgres-raw-results.md](postgres-raw-results.md)

**Setup:** PostgreSQL 18.0 (Windows, local), Npgsql 11.0.0, .NET 11. A scratch database is created per run. Silent network loss is simulated with an in-process TCP proxy that stops forwarding but keeps its sockets open, like a hung load balancer or an expired NAT entry.

## Results

### A. Latency and throughput: **PASS**

| Measurement | Result |
|-------------|--------|
| Commit → listener event, 1,000 sequential transactions | p50 **0.22 ms**, p95 0.38 ms, p99 0.50 ms, max 2.3 ms |
| Burst: 8 senders × 2,500 autocommit notifies | 20,000 sent in 1.97 s (about 10,000/s); **all 20,000 received** |

### B. Transaction semantics: **PASS**, with free de-duplication

| Scenario | Delivered |
|----------|-----------|
| One transaction: 100 × identical payload + 3 distinct payloads | **4**: identical channel + payload pairs collapse within a transaction |
| Notify, then rollback | 0 |
| Notify, savepoint, notify, `ROLLBACK TO SAVEPOINT`, commit | only the first |
| Same payload in two separate transactions | 2 |

The per-transaction insert debounce in design §4.3 therefore comes from Postgres itself: KQ can call `pg_notify` once per inserted row and still send at most one notification per queue per transaction. A client-side debounce is still worth having, to save round trips.

### C. Payload limit

- 7,999 bytes: OK.
- **8,000 bytes: error 22023**, "payload string too long". The limit is in bytes: 2,700 × `☕` (8,100 UTF-8 bytes) fails too.

KQ payloads are tiny, but control messages (for example a cancel with job ids) must be capped or split.

### D. Channel names

- `LISTEN public.river_insert` without quotes is a **syntax error (42601)**. The quoted form `LISTEN "public.river_insert"` works.
- An identifier over 63 bytes is **silently truncated** by `LISTEN`; only a NOTICE is raised. `pg_notify` with the same long name **fails (22023)**. The two sides then never meet.

→ KQ always quotes channel names. It validates that `len(schema) + len(".river_leadership")` ≤ 63 bytes, i.e. **schema name ≤ 46 bytes** when notifications are enabled. It refuses to start otherwise, or falls back to poll-only with a warning.

### E. LISTEN on a pooled connection: **dropped silently**

The connection was returned to the pool and reopened as the same physical connection (same PID). `pg_listening_channels()` was then empty and no notifications arrived: the pool reset (`DISCARD ALL`) removed the LISTEN.

→ The notifier must open its own **non-pooled** connection. It clones the data source's connection string with `Pooling=false` and never hands it out.

### F. Server-side disconnect (`pg_terminate_backend`): **detected at once**

Three rounds:
- `WaitAsync` threw `PostgresException 57P01` **1–2 ms** after the terminate, and the connection state was `Broken`.
- Reconnect + LISTEN took 47–60 ms.
- **0 of the 5 notifications** sent while disconnected arrived after reconnect: Postgres does not buffer notifications for a channel nobody is listening on.

→ After every reconnect the notifier must **wake every producer and the elector**, so they fetch or elect immediately. This resync replaces whatever notifications were lost.

### G. Silent connection loss (proxy black-hole)

| Strategy | Failure detected after |
|----------|------------------------|
| Plain `WaitAsync()`, no keepalive | **never** (40 s cap) |
| Npgsql **`Keepalive=2`** | **3.5 s** (`NpgsqlException` → `TimeoutException`) |
| Npgsql `Keepalive=10` | 19.5 s |
| `WaitAsync(2 s)` + `SELECT 1` probe with `Command Timeout=2` | 33.5 s: the command timeout plus the cancel round trip, which also hangs |
| `Delay(2 s)` + `SELECT 1` probe with `Command Timeout=2` | 33.5 s |
| `WaitAsync(2 s)` + `SELECT 1` probe + 3 s external watchdog | 4.5 s, but **`DisposeAsync` on the dead connection then hung for more than 5 s** and had to be abandoned |

Findings:
- A notifier blocked in `WaitAsync` **never notices** a silently dead connection. Producers would then fall back to polling without anyone knowing.
- Npgsql's built-in `Keepalive` is the simplest reliable detector. It took about **2 × Keepalive** here.
- `Command Timeout` does not bound a probe on a black-holed socket in practice, because the cancellation request goes through the same dead path.

→ The notifier connection sets **`Keepalive=5`** by default (detection in about 10 s), configurable as `NotifierKeepAlive`. It disposes broken connections **in the background, with a timeout**, and never awaits them on the reconnect path.

## PgBouncer: **not run**

Neither Docker nor a PgBouncer binary was available on this machine. Known PostgreSQL and PgBouncer behaviour, still unverified here:
- **Transaction-mode** pooling does not support LISTEN. A LISTEN is lost as soon as the server connection returns to the pool, the same effect as in section E.
- **Session mode** works.

The design already handles this: NFR-COMP-04 says poll-only mode through transaction pooling. The new `NotifierConnectionString` option lets the notifier bypass PgBouncer and go straight to Postgres. The PgBouncer cases (transaction mode in poll-only, and the notifier bypass) move to the CI matrix, which has Docker, as M2 task 2.11.

## Decisions

| # | Decision | Where |
|---|----------|-------|
| D1 | The notifier owns **one dedicated, non-pooled connection**: the cloned string with `Pooling=false` and `Keepalive=5` by default | Design §3 (Notifier), §7 options |
| D2 | **Resync on (re)connect:** after every successful LISTEN (first or later), the notifier raises a "wake all" to every producer and the elector | Design §3, §5.1 |
| D3 | Dead connections are disposed in the background with a 5 s timeout; reconnects use exponential backoff from 100 ms to 30 s, with jitter | Design §3 |
| D4 | Channel names are always quoted. Schema name ≤ 46 bytes when notifications are on, validated at startup | Design §4.3, options validation |
| D5 | Payloads ≤ 7,999 bytes, enforced by the control API | Design §4.3 |
| D6 | No client-side per-row debounce is needed for correctness, because Postgres collapses identical notifies per transaction. KQ still sends one `pg_notify` per distinct queue per insert batch | Design §4.3 |
| D7 | New option `NotifierConnectionString`, for PgBouncer or proxy setups. PgBouncer tests move to CI (M2 task 2.11) | Design §7, plan |
| D8 | `NotifierHealthy` is exposed as a health check signal (M6 task 6.5) so a silently broken notifier is visible | Plan M6 |

## Limitations

- Local loopback only; real network round trips will add latency.
- The black-hole simulation stops forwarding in both directions. Real-world one-way loss is likely to behave the same with app-level keepalive.
- No managed Postgres (RDS, Azure, Neon) and no PgBouncer.
