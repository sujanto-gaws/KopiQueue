# Spike 0.9 — SQL Server: fetch correctness, isolation and locking

**Date:** 2026-11-26 · **Plan task:** M0 / 0.9 · **Requirements:** FR-EXE-01, NFR-REL-06 · **Risk:** R10
**Code:** `spikes/SqlServerSpikes` (`fetch`, `isolation`, `escalation`, `plan`) · **Raw output:** [sqlserver-raw-results.md](sqlserver-raw-results.md)

## Questions

1. Does the design §8.1 fetch (`UPDLOCK, READPAST, ROWLOCK` on an updatable CTE) hand every job to exactly one fetcher under heavy concurrency, with READ_COMMITTED_SNAPSHOT (RCSI) both off and on?
2. How does it behave next to uncommitted work, and on sessions using SNAPSHOT isolation?
3. When do fetch and complete statements escalate to table locks?

## Setup

SQL Server 2019 Developer (15.0.2210), 16 logical CPUs, client on the same machine (.NET 11, Microsoft.Data.SqlClient 7.1.2).
Two scratch databases: `kopi_spike_rc` (RCSI off) and `kopi_spike_rcsi` (RCSI on, the Azure SQL Database default). Both allow SNAPSHOT.
Schema: design §4.4 `kopi_job`, with its six indexes. Workers do no work.

## Results

### Concurrency (0.9a): **PASS**

| Database | Fetchers × limit | Completers | Jobs | Fetched once / completed | Duplicates | Deadlocks | Throughput |
|----------|------------------|-----------|------|--------------------------|-----------|-----------|------------|
| RCSI off | 16 × 25 | 2 | 20,000 | 20,000 / 20,000 | 0 | 0 | 9,563 jobs/s |
| RCSI on | 16 × 25 | 2 | 20,000 | 20,000 / 20,000 | 0 | 0 | 9,576 jobs/s |
| RCSI on | 64 × 5 | 4 | 20,000 | 20,000 / 20,000 | 0 | 0 | 4,506 jobs/s |

Every row ended with `attempt = 1`, so no job was fetched twice. The completer used batched OPENJSON updates of up to 500 rows.

### READPAST semantics (0.9b): **as designed, on both databases**

| Check | Result |
|-------|--------|
| Rows locked by another in-flight fetch | Skipped, not waited on (1 ms). No overlap. After that transaction rolls back, the same rows are fetched again |
| Jobs inserted by an uncommitted caller transaction | Invisible to the fetch, which does not block (0 ms). Fetched right after commit |

### Isolation (0.9b): **two findings**

| Check | Result |
|-------|--------|
| `SET TRANSACTION ISOLATION LEVEL SNAPSHOT`, close, reopen from the pool | **The SNAPSHOT level survives the pool reset** (same session) |
| `BeginTransaction(IsolationLevel.Snapshot)`, commit, reopen from the pool | **The SNAPSHOT level survives** |
| Fetch on a SNAPSHOT session | **Fails: error 650** ("READPAST only in READ COMMITTED or REPEATABLE READ") |
| Fetch with a `SET TRANSACTION ISOLATION LEVEL READ COMMITTED;` prefix in the same batch | Works. The session is back to SNAPSHOT afterwards, because the SET is scoped to the `sp_executesql` batch |

### Lock escalation and plan stability (0.9c / 0.9d): **one finding**

Without a hint, the **fetch plan flips** at larger limits. On a 36,000-row table it uses a filtered-index seek at limit 25, but a **clustered index scan + sort** at limit 1,000.
The scan with `UPDLOCK` reads every row (ActualRowsRead = 36,000) and **escalates to a table X lock**, which blocks every other producer.

| Statement | 1,000 rows | 4,000 | 4,900 | 6,000 |
|-----------|-----------|-------|-------|-------|
| Fetch, no hint | **escalated** (scan) | **escalated** (scan) | — | — |
| Fetch, `INDEX(kopi_job_fetch_idx)` or `FORCESEEK(kopi_job_fetch_idx(queue))` | row locks (4,000 keys) | row locks (16,000 keys) | row locks | **escalated** |
| Batch complete (OPENJSON join) | row locks (4,000 keys) | row locks | row locks (19,600 keys) | **escalated** |

Each row a statement touches takes one key lock **per index it maintains** (4 for fetch and complete). Escalation fires once one index passes about 5,000 locks in a single statement.
With the hint, rows read = 2 × limit, whatever the table size.

## Decisions and design changes

| # | Change | Where |
|---|--------|-------|
| D1 | The fetch uses **`FORCESEEK(kopi_job_fetch_idx(queue))`** in addition to `UPDLOCK, READPAST, ROWLOCK` | Design §8.1 |
| D2 | Every SQL Server statement that uses READPAST (fetch, scheduler, rescuer, cleaner) starts with **`SET TRANSACTION ISOLATION LEVEL READ COMMITTED;`**. The SET is batch-scoped, so it never changes a session it shares with application code | Design §8.1 |
| D3 | The driver connection string gets **`Application Name=KopiQueue`** by default. This gives KQ its own connection pool, so it does not inherit session state from application code, and makes KQ sessions identifiable in DMVs. Belt and braces with D2 | Design §8.1 |
| D4 | **Hard cap of 2,000 rows per statement** for fetch (`FetchBatchMax`), complete and maintenance, below the escalation threshold with margin | Design §8.1, FR-QUE-01 note |
| D5 | Each SQL Server statement with locking hints gets a **plan-shape test**: run it with `SET STATISTICS XML ON` at small and large limits and assert a seek and no escalation | Plan M5 task 5.8 |
| D6 | No deadlocks seen, but deadlock retry (error 1205) stays in the design (R10). Synthetic tests are not proof | — |

## Limitations

- SQL Server 2019 only, on one machine. 2022, 2025 and Azure SQL are covered later by the CI conformance matrix and M7 task 7.4.
- No-op workers, at most 36,000 rows per test, no failover or killed sessions (that is M7's chaos suite).
- The throughput figures include client and server on the same 16-core box. Treat them as relative, not as targets.
