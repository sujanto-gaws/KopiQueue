# Spike 0.10 — SQL Server: unique jobs, bulk insert, polling

**Date:** 2026-11-26 · **Plan task:** M0 / 0.10 · **Requirements:** FR-UNQ-02/03, FR-INS-04, FR-DB-04, NFR-PERF-07 · **ADR:** 011
**Code:** `spikes/SqlServerSpikes` (`unique`, `snapshot`, `bulk`, `poll`) · **Raw output:** [sqlserver-raw-results.md](sqlserver-raw-results.md)

Same setup as [spike 0.9](0.9-sqlserver-fetch-and-locking.md): SQL Server 2019 Developer, local, RCSI off and on.

## A. Unique inserts under concurrency

Two strategies, both with the `unique_slot` index (ADR-011) as the final guarantee:

- **HoldLock** (design §8.1 as drafted): `INSERT ... WHERE NOT EXISTS (SELECT ... WITH (UPDLOCK, HOLDLOCK))`.
- **AppLock** (alternative): `sp_getapplock` on `kopi_unique:<key hex>`, owned by the transaction, then `NOT EXISTS (... WITH (READCOMMITTEDLOCK))`.

### Correctness: **both PASS**

About 2,400 inserts per strategy per database, with RCSI off and on: 0 duplicate occupied keys, 0 errors, 0 deadlocks. A hot key always gave exactly one insert per round and returned *skipped* to everyone else.

### Latency (RCSI on; RCSI off is within noise)

| Scenario | HoldLock p50 / p95 / max | AppLock p50 / p95 / max |
|----------|--------------------------|-------------------------|
| Hot key, 100 concurrent, autocommit | 3.9 / 76 / 92 ms | 21.9 / 49 / 76 ms |
| Distinct keys, 100 concurrent, autocommit | 8.0 / 16 / 34 ms | 9.1 / 15 / 40 ms |
| Hot key, 20 callers, tx held 50 ms | 621 / 1,179 / 1,241 ms | 623 / 1,183 / 1,245 ms |
| **Distinct keys, 50 callers, tx held 50 ms, empty table** | **122 / 2,659 / 3,095 ms** | **60 / 67 / 67 ms** |
| Distinct keys, 50 callers, tx held 50 ms, 20,000 existing keys | 58 / 64 / 120 ms | 62 / 63 / 77 ms |

**Finding: HoldLock blocks unrelated keys.** `HOLDLOCK` takes *key-range* locks. When few unique keys exist (a new install, or just after the cleaner ran), unrelated keys fall into the same index gap. They then serialise behind each other's caller transactions: p95 2.7 s for keys that have nothing in common.
AppLock locks only the exact key, so it shows no such blocking. Real serialisation on a *hot* key costs the same for both strategies, and is inherent: PostgreSQL's `ON CONFLICT` also waits for the conflicting transaction.

### Callers with SNAPSHOT isolation or XACT_ABORT ON

| Scenario | Result (both strategies) |
|----------|--------------------------|
| READ COMMITTED caller, `XACT_ABORT ON`, duplicate key | `Skipped`, transaction intact (`XACT_STATE = 1`), commit OK |
| SNAPSHOT caller, new key | `Inserted`, commit OK |
| SNAPSHOT caller, key committed by another transaction **after** the snapshot started | First version: **neither inserted nor skipped**. The locking `NOT EXISTS` saw the row, but the plain fallback `SELECT` read the older snapshot and returned nothing. **Fixed** by adding `WITH (READCOMMITTEDLOCK)` to the fallback `SELECT`: now `Skipped` with `XACT_ABORT` both OFF and ON, transaction intact |

No 2601 (unique violation) or 3960 (snapshot update conflict) errors reached the caller in any scenario.

## B. Bulk insert inside a caller transaction

50,000 jobs (4,000 for the first row), rolled back once and then committed. While the transaction was open, another connection fetched from a **different queue** with a 3 s timeout.

| Method | Rows/s | Rollback leaves 0 rows | Locks held | Concurrent fetch on another queue |
|--------|--------|------------------------|------------|-----------------------------------|
| SqlBulkCopy, CheckConstraints, 4,000 rows | 37,546 | yes | PAGE/X 488, EXTENT/X 36 | **BLOCKED** (timeout) |
| SqlBulkCopy, CheckConstraints | 38,280 | yes | PAGE/X 4,975, EXTENT/X 321 | **BLOCKED** |
| SqlBulkCopy, no CheckConstraints | 43,973 | yes | same | **BLOCKED**, and **all 8 CHECK constraints left untrusted** |
| SqlBulkCopy, CheckConstraints, `LOCK_ESCALATION = DISABLE` | 35,088 | yes | same | **BLOCKED** |
| **OPENJSON `INSERT ... SELECT`, 1,000 rows per statement, ids returned** | **41,825** | yes | KEY/X 200,000 (row locks only) | **not blocked** |

**Finding:** SqlBulkCopy takes **page and extent X locks** even for small loads and with escalation disabled. `READPAST` skips row locks but **not page locks**, so every producer can stall until the caller commits.
Batched OPENJSON inserts are about as fast, return the new ids, keep row locks, and do not block fetchers.

## C. Poll cost and pickup latency

Table: 200,000 completed jobs, plus 50,000 available jobs in another queue.

| Measurement | Result |
|-------------|--------|
| Empty poll, client round trip | p50 0.1 ms, p99 0.6 ms |
| Empty poll, server | **3 logical reads, 70 µs CPU**; filtered-index seek, no scans |
| Fetch 25 from a busy queue | p50 3.2 ms round trip; **950 logical reads, 2.5 ms CPU** |
| Pickup latency, poll every 100 ms | p50 76 ms, p95 111 ms, max 124 ms |
| Pickup latency, poll every 1 s | p50 515 ms, p95 997 ms, max 997 ms |

Idle polling is cheap. 10 clients × 10 queues × 100 ms is about 1,000 polls/s, roughly 70 ms of server CPU per second.
Latency is about half the interval plus a few ms, as expected. The busy fetch costs about 38 logical reads per job: index maintenance on every index, Halloween-protection spools, and the `attempted_by` `nvarchar(max)` write. This is an optimisation target for M5.

## Decisions and design changes

| # | Change | Where |
|---|--------|-------|
| D1 | **ADR-011 revised: unique inserts use `sp_getapplock`** (transaction-owned, resource `kopi_unique:<schema>.<prefix>:<key hex>`) plus `READCOMMITTEDLOCK` checks. The `unique_slot` index stays as the final guarantee. Without a caller transaction, the batch opens and commits its own | Design §8.1, ADR-011 |
| D2 | The fallback `SELECT` that returns the existing duplicate uses **`WITH (READCOMMITTEDLOCK)`**, which SNAPSHOT callers need | Design §8.1 |
| D3 | **SqlBulkCopy dropped** from the SQL Server driver (new ADR-014). `InsertManyAsync` and `InsertManyFastAsync` use batched OPENJSON inserts of ≤ 1,000 rows per statement. SqlBulkCopy may come back post-1.0 as an explicit offline-import mode, always with `CheckConstraints` | FR-INS-04, design §8.1 |
| D4 | NFR-PERF-07 initial SQL Server targets (validated again in M5/M7 on CI hardware): end-to-end no-op throughput ≥ 5,000 jobs/s per client; batched insert ≥ 30,000 jobs/s; cross-process pickup p50 ≤ interval/2 + 30 ms; empty poll ≤ 10 logical reads | Requirements NFR-PERF-07 |
| D5 | The SQL Server default `FetchPollInterval` stays at 1 s. 100 ms is documented as safe (cost measured above) | Design §7 |
| D6 | M5 performance item: reduce the busy-fetch cost of 950 logical reads per 25 jobs. Check whether `unique_slot` maintenance for NULL keys can be avoided; move `attempted_by` trimming or storage off the hot path; check spool elimination | Plan M5 task 5.9 |

## Limitations

SQL Server 2019 Developer only, local, synthetic no-op load, tables ≤ 250,000 rows. The applock approach must still be validated on Azure SQL Database (M7 task 7.4). Lock-memory-driven escalation, which fires on memory pressure rather than lock count, was not exercised.
