# Spike 0.8 — River schema shape, wire behaviour, unique keys

**Date:** 2026-11-26 · **Plan task:** M0 / 0.8 · **Requirements:** NFR-COMP-05, FR-DB-08, FR-UNQ-01..04, FR-INS-07 · **ADR:** 001, 002
**Code:** `spikes/RiverSchema` (`introspect.sql`, `observe/` Go harness, `golden/`) · **Raw output:** [postgres-raw-results.md](postgres-raw-results.md)

## Method (clean-room, C2)

River's source was **not read**. Everything below comes from three black-box sources:

1. **Catalog introspection.** A scratch database was migrated with River's own CLI, then read from `pg_catalog` (`introspect.sql`). The output records names, types, defaults, constraints and indexes: the interface. Function bodies were deliberately not selected.
2. **Behaviour observation.** A Go harness uses only River's public API (`river.NewClient`, `Insert`, `InsertTx`, workers, `Subscribe`). It records what lands in the tables and on LISTEN/NOTIFY.
3. **Golden vectors.** River computed unique keys for a corpus of 22 inputs. A Python model written only from those outputs reproduces all 22 (`golden/verify_unique_keys.py`).

**Setup:** PostgreSQL 18.0 (Windows, local) and **River v0.51.2**, the latest on the Go proxy on 2026-11-09. The locally installed v0.31.0 was outdated and was not used.

**Objects:**
- Tables: `river_job`, `river_leader` (UNLOGGED), `river_migration`, `river_notification`, `river_queue`.
- Sequences: `river_job_id_seq`, `river_notification_id_seq`.
- Enum: `river_job_state` (available, cancelled, completed, discarded, pending, retryable, running, scheduled).
- Function: `river_job_state_in_bitmask(bit, river_job_state) → boolean` (SQL, IMMUTABLE).
- No triggers and no views. There are **no** `river_client` or `river_client_queue` tables, which closes DQ-4.

**Differences from design v0.3 §4.1** (applied in design v0.4):

| Item | Design v0.3 | River v0.51.2 |
|------|-------------|---------------|
| `river_notification` table | missing | `id bigint` (sequence), `created_at`, `payload text`, `topic text`; `topic_length` CHECK (1–127); indexes on `created_at` and `(topic, id)`. It stayed **empty** in every PostgreSQL run: an outbox for drivers without LISTEN/NOTIFY |
| `max_attempts` default | none | `25` |
| Length CHECKs (`kind`, `queue`, `leader_id`, `line`) | `BETWEEN 1 AND 128` | `> 0 AND < 128`, i.e. **1–127** |
| `river_migration` CHECKs | none | `line_length` (1–127), `version_gte_1` |
| `river_queue.updated_at` | no default | `DEFAULT CURRENT_TIMESTAMP` |
| `river_leader.name` | PK, default, `CHECK (name = 'default')` | same; the constraint is named `name_length` |
| `id` | `bigserial` | `bigint DEFAULT nextval('river_job_id_seq')`, which is equivalent |

The indexes match the design exactly:
- `river_job_prioritized_fetching_index`
- `river_job_state_and_finalized_at_index` (partial)
- `river_job_kind`
- GIN on `args` and `metadata`
- the partial unique `river_job_unique_idx`

## B. Behaviour observed through River's public API

| Observation | Consequence for KQ |
|-------------|--------------------|
| **Channels are schema-qualified.** A running client's LISTEN shows as `LISTEN "public.river_control"`. An insert produced a NOTIFY on channel **`public.river_insert`** with payload `{"queue": "default"}` | Channel = `"<schema>.river_<topic>"`, always quoted. Design §4.3 used bare names, which a River client would not hear |
| The payload is jsonb text (`": "` with a space) | Parse payloads as JSON; never compare strings |
| Insert-only client (no workers) with `InsertTx` then rollback: no row remains | Matches FR-INS-02 |
| A job scheduled +1 h is inserted with `state = scheduled` | Matches §4.2 |
| Live insert → completed on a started client: about 110 ms; `attempted_by = ["<host>_<UTC yyyy_MM_ddTHH_mm_ss_ffffff>"]` | Client ID format is free-form; KQ's `{machine}-{pid}-{random}` is compatible |
| A working client creates `river_queue` rows (`metadata {}`, `paused_at NULL`); `river_leader` is empty after a graceful stop | Matches §5.5 (resign deletes the row) |
| Tags are validated client-side: `"t1"` was rejected with `tags should match regex \A[\w][\w\-]+[\w]\z` | KQ applies the same rule (≥ 3 characters, word characters and `-`) and returns its own error message |
| `ByArgs` rejects args that are not a JSON object (a Go map type failed with "expected struct") | KQ: args must serialise to a JSON object. Already true for record types |
| `ByState` must contain **pending, running, scheduled**, otherwise the insert is rejected | Consistent with FR-UNQ-04 |

Not confirmed, and moved to the M2 River-interop suite (plan task 2.10):
- whether an insert-only River client also sends NOTIFY;
- whether a River client subscribes to `river_leadership`.

`pg_stat_activity` shows only the last statement per backend, so it cannot answer either question.

## C. Unique key and unique states: reconstructed rule

**Golden vectors:** `spikes/RiverSchema/golden/river-v0.51.2-unique-keys.jsonl`, 22 inputs, every one reproduced.

```
unique_key = SHA-256( concat of, in this order and only when enabled:
    "&kind="   + kind                      -- omitted when ExcludeKind
    "&args="   + canonical_args             -- ByArgs
    "&period=" + RFC 3339 UTC, seconds, "Z" of floor(now / period) * period   -- ByPeriod
    "&queue="  + queue                      -- ByQueue
)                                           -- 32 bytes, stored in unique_key bytea

canonical_args = "{" + join(",", key_json + ":" + value_raw  for top-level members sorted by key, bytewise) + "}"
    -- only members whose field is marked unique, if the type has any
    -- value_raw = the member's value text exactly as the producer serialised it (not re-encoded)
```

Confirmed by the vectors:
- **Top-level keys are sorted** (bytewise: `Mid` < `_u` < `alpha` < `zeta`). **Nested values are copied verbatim**: `{"inner":{"b":"b","a":2}}` hashes in struct order, not re-sorted.
- Because values are copied verbatim, **the producer's JSON encoding is part of the key**. Go's `encoding/json` escapes `<`, `>` and `&` as `<`, `>` and `&`, and also `U+2028` and `U+2029`; it does not escape other non-ASCII characters; it writes numbers like `1e-7` and `1e+21`. `System.Text.Json` with default options escapes differently (`<`, and all non-ASCII), so it gives **different keys for the same logical args**.
- The **state set is not part of the key**. Different `ByState` values with the same dimensions dedupe against each other, and the first row's `unique_states` wins.
- **The period length is not part of the key.** `ByPeriod = 15m` and `1h` collided when both truncated to 01:00:00Z.
- With field tags, untagged members are ignored, and `omitempty` members that are empty are absent from the key.
- `ExcludeKind` drops the `&kind=` part entirely.

**`unique_states` bit mapping** (`bit(8)` text, left to right): `scheduled, running, retryable, pending, discarded, completed, cancelled, available`. This is the reverse of the enum's sort order. The default is `11110101` (everything except cancelled and discarded). The SQL Server `tinyint` (design §4.4) uses the same positions, with bit 7 = scheduled.

**Consequence (DQ-8, new).**
- KQ will always produce River-identical keys for args whose JSON encoding is byte-identical to Go's.
- For mixed Go and .NET producers of the *same* unique job, the .NET side needs Go-compatible escaping and the same nested member order.
- Proposal: by default, KQ's unique-key hasher re-serialises each top-level value with a `Utf8JsonWriter` set to Go-compatible escaping. Users with exotic types can override it with `IUniqueKeyEncoder`. Decide in M4 (task 4.1) with the golden vectors as the acceptance test.

## Decisions

| # | Decision | Where |
|---|----------|-------|
| D1 | **Pin River schema `main` v8 (River v0.51.2).** The KQ migrator creates exactly these objects, including `river_notification`, so a later `river migrate-up` sees a consistent schema | Design §4.1, ADR-002 |
| D2 | Fix the §4.1 DDL: `max_attempts DEFAULT 25`, length CHECKs `< 128`, `river_migration` CHECKs, `river_queue.updated_at DEFAULT`, `river_notification` | Design §4.1 |
| D3 | Channels are `"<schema>.river_insert"`, `"<schema>.river_control"` and `"<schema>.river_leadership"`, always quoted. Payloads are parsed as JSON | Design §4.3 |
| D4 | Unique key algorithm as above. The 22 golden vectors become unit tests in M4 task 4.1. The unique state set is **not** hashed | Design §5.6 |
| D5 | DQ-4 is closed: there are no `river_client*` tables at the pinned version | Design DQ-4 |
| D6 | New DQ-8: Go-compatible JSON encoding for unique keys | Design DQ-8 |
| D7 | Tag validation: `\A[\w][\w\-]+[\w]\z`, max 255 characters | Requirements FR-INS (tags) |

## Limitations

- One River version (v0.51.2) and PostgreSQL 18 only.
- `river_notification` usage was inferred, not exercised.
- `ByPeriod` truncation was verified only for 15 m, 1 h and 24 h, at whole-second insert times.
- No sub-second or leap-second edge cases were tested.
